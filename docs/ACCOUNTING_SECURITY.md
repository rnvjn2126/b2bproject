# Accounting security

The initial accounting endpoints are restricted to the workspace owner. Existing sales and manager roles receive no finance access automatically. Owner access is independent of provisional subscription tiers. Requests use Django login, CSRF, and inherited private response headers. Forms restrict foreign keys to the current workspace, and posting revalidates that boundary.

The app has no update or delete routes or admin registration for posted journals. Journal records store the actor and timestamp, and reversal records point to their source. The audit screen reads postings, reversals and period locks within the current company. Migration 0004 installs SQLite and PostgreSQL triggers to reject changes to sealed journals and their lines, appending lines to sealed journals, and changes to locked periods. It also prevents sealing a journal with an invalid period, a foreign ledger or unequal amounts.

The application role must have no schema-change, trigger-management or truncate permission in production. These guards do not protect against a privileged database operator. Verify PostgreSQL migrations and concurrent transactions against an isolated synthetic database, establish independent tamper evidence, restrict finance roles, and test backups and restoration before release. On SQLite, the guards intentionally reject a flush of a populated accounting database. Use rollback-based tests or disposable databases for transaction and migration probes. Schema changes that rebuild guarded SQLite tables must preserve or reinstall the guards and be verified by the immutability tests.

Voucher drafts, editing and approval are owner-only and company scoped. Approval uses a CSRF-protected POST and rechecks the reviewed revision under the same lock as posting. Replayed approval returns the existing journal. Existing direct journal and cash voucher workflows remain owner-only.
